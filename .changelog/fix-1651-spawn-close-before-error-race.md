section: Fixed

- **The #1605 lifecycle-smoke lane's phase 5 now genuinely exercises an absent `gh`, instead of quietly answering with a real one (refs #1651)** — phase 5 pinned outcome `"missing"` for a genuinely-absent `gh` binary, and passed on Windows but got `"non-installable"` on Linux CI. Dispatching the real workflow against two rounds of a `safeSpawnAsync` close/error-race fix (a real, if narrow, Node hazard — see below) still failed byte-identically, so a debug pass added a raw `spawnSync("gh", ["auth", "token"])` probe right where the lane's own removal happens. It answered `status: 1, stderr: "no oauth token found for github.com"` — a genuine, correctly-completed `gh` run. GitHub-hosted `ubuntu-latest` runners carry a *second* `gh` on PATH that `which gh` doesn't report first; the lane's PATH exclusion only stripped the one `which` did report, leaving the other one reachable the moment the fixture was deleted. Phase 5 was never testing a missing binary on Linux at all — it was asking the classifier to explain a real rejected-auth answer while asserting the missing-tool verdict. `classifyGhTokenFailure` was correct both times; the harness's setup was not. `findAllOnPath`/`pathWithoutDirsOf` (`which -a` on POSIX; Windows' `where` already lists every match) now exclude every directory holding a `gh`, not just the first.
  - `scripts/smoke-availability-lifecycle.mjs` — `findAllOnPath` (was `findOnPath`, single-match) and `pathWithoutDirsOf` (was `pathWithoutDirOf`, single-dir).

- **`safeSpawnAsync` also decides a never-started spawn from the `close` event's own shape now, not from `error`'s arrival timing** — a genuine, if narrower, hazard surfaced while chasing the above: Node's docs leave the `error`/`close` event order unspecified for a child that never launched, and the real shape for that case is a negative code (`-2` for ENOENT on Linux, `-4058` on Windows), with `error` sometimes landing a full tick later via `setImmediate`/`process.nextTick`. The `close` handler now decides straight from `code === null || code < 0` — a shape no completed process ever produces — independent of whether or when `error` fires, reusing `error`'s Error when it's already available and synthesizing an ENOENT-shaped one otherwise. A single `resolved` flag lets whichever handler decides first win outright, including the inverse case: a healthy `close(0, null)` must never be downgraded by a late, unrelated `error` (e.g. a post-exit `kill()` failing with `EPERM`). `classifyGhTokenFailure` also gets a belt: it no longer trusts a bare `!res.error` as proof `gh` ran and answered — a `null`/negative `status` alone (OS-independent, read off Node's own report) now routes through the missing/transient handling regardless of whether `error` happened to be attached. This did not turn out to be what made phase 5 fail (the harness bug above did), but it closes a real correctness gap this investigation surfaced.
  - `clients/safe-spawn.ts` — the `close`/`error` handlers inside `safeSpawnAsync`.
  - `clients/zizmor-config.ts` — `classifyGhTokenFailure`'s `neverAnswered` guard.
  - `tests/clients/safe-spawn-close-before-error-race.test.ts` — regression tests for the `close(-2, null)`/`close(null, null)` shapes (with and without a delayed or absent `error`) and the healthy-run non-inversion case.
