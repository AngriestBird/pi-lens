section: Fixed

- **`safeSpawnAsync` no longer misreads a spawn that never started as a clean run when `close` wins the race against `error` (refs #1651)** — the lifecycle-smoke lane's phase 5 pinned a genuinely-absent `gh` binary as classifying `missing` on Windows but `non-installable` on Linux CI. Root cause: Node's own docs leave the `error`/`close` event order unspecified for a child that never launched (ENOENT), and the `close` handler only guarded against firing *after* `error` (`if (spawnErrored) return;` at entry) — when `close` fired first instead, with the `status: null, signal: null` shape only a never-started process produces, the handler fell through to the "completed successfully" branch and resolved `{ status: null, error: undefined }`. Downstream, `classifyGhTokenFailure`'s `!res.error` check then read that as a durable rejected-token answer (`non-installable`) instead of a missing binary (`missing`). Windows rarely hit this because `resolveWindowsCommand` fails closed on an unresolvable bare command before any real `spawn()` call ever runs; Linux (and any Windows command that resolves but is later removed) always goes through the raw event path and can lose the race. The `close` handler now re-checks `spawnErrored` after its own `await` point, so a coincident `error` — already synchronously delivered by that point — wins regardless of which event fired first. The lifecycle-smoke lane's phase 5 assertion (`outcome === "missing"`) was already the justified verdict; it needed no change.
  - `clients/safe-spawn.ts` — the `close` event handler inside `safeSpawnAsync`.
  - `tests/clients/safe-spawn-close-before-error-race.test.ts` — new regression test, proven red on pre-fix code.
